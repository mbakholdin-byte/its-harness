# Self-Correction (Самокоррекция)

## Когда активировать этот скилл

- **bgagent висит ≥ 6 мин без `last_tools`**, и ты собираешься «попробовать ещё раз» сменив модель/провайдер/имя — **СТОП**. Это ловушка: скорее всего, проблема в spawner opencode, а не в параметрах вызова. Проверь: (а) жив ли другой агент на той же инфраструктуре, (б) пробовал ли ты уже 2+ разных комбинации параметров — если да, изоляция переменных провалена, остановись и спроси руководителя
- Одна и та же команда/инструмент упали **2 раза** с одинаковой или похожей ошибкой.
- Скрипт выполнился «успешно», но **не выдал результата** или выдал неожиданный результат.
- Ты собираешься **повторить план**, который уже озвучивал в этой сессии.
- Ты собираешься **повторно запросить данные**, которые уже получил.
- Ты чувствуешь желание «попробовать ещё разок» тем же способом.

## Алгоритм: СТОП → ДИАГНОЗ → СМЕНА → ЗАПИСЬ

### Шаг 1 — СТОП
- НЕ выполняй следующую команду.
- Явно напиши: «Активирую самокоррекцию.»

### Шаг 2 — ДИАГНОЗ
Ответь на вопросы:
1. Что именно сломалось? (Скопируй сообщение об ошибке или опиши симптом.)
2. Почему это произошло? (Корневая причина, а не просто симптом.)
3. Это та же корневая причина, что и у предыдущего сбоя в этой сессии?
4. Какой подход я использовал? (Python-скрипт через bash, PowerShell, curl и т. д.)

### Шаг 3 — СМЕНА СТРАТЕГИИ
Выбери **принципиально другой** подход:

| Что не сработало | На что переключиться |
|---|---|
| Python-скрипт через bash (ошибка кодировки) | curl к REST API |
| PowerShell-скрипт (ошибка кодировки) | curl к REST API |
| write создал битый файл | write + немедленная проверка через read |
| Скрипт работает, но нет вывода | Сначала read файла скрипта, проверить содержимое |
| bgagent молчит, попытка сменить модель | Не менять модель вслепую. Сначала проверить: `curl :8002/health`, `curl :8004/health`, проверить, что JSON-ключ в opencode.json. Если всё ОК и другая задача на той же инфраструктуре тоже висит — перезапустить opencode, не менять конфиг |
| API-вызов падает (таймаут/ошибка) | Повторить с меньшим payload или другим endpoint |
| Сложный многошаговый скрипт | Разбить на маленькие однозадачные команды |

### Шаг 4 — ЗАПИСЬ
После решения проблемы:
- Запомни, что сработало, в контексте текущей сессии.
- Если это переиспользуемый урок — предложи обновить FAS_DECISIONS.md.

## Чек-лист перед повторной попыткой
Перед повтором ЛЮБОЙ упавшей операции проверь ВСЁ из списка:
- [ ] Я понимаю, ПОЧЕМУ предыдущая попытка провалилась (а не просто ЧТО случилось).
- [ ] Мой новый подход принципиально отличается от провалившегося.
- [ ] Если пишу файл — перечитаю его сразу после записи.
- [ ] Если использую print() на Windows — НЕ вывожу не-ASCII в консоль.
- [ ] Если запрашиваю данные — проверил, что их ещё нет в кэше.
- [ ] Я НЕ превысил 2 неудачи с этим конкретным подходом.

## Известные проблемы

Справочник известных проблем (Windows/кодировка, Qdrant, инструмент write) вынесен в `known-issues.md` рядом с этим файлом — читай при соответствующих симптомах.

## Паттерн-детекция ошибок

Если повторяющаяся ошибка связана с активным skill — активируй **skill-evolution**: запись эволюции в `_evolutions.json` и создание instinct с confidence 0.3 (см. секцию «Инстинкты» там).

## Эскалация
Если ты:
- Провалился с 3+ разными подходами (по 2 попытки = 6+ сбоев всего)
- Потратил более 50% бюджета шагов без прогресса

Тогда ОСТАНОВИСЬ и скажи пользователю:
1. Какая задача стояла.
2. Что ты пробовал (список подходов).
3. Что не сработало и почему.
4. Что рекомендуешь сделать вручную.

## Независимая верификация результата

После самостоятельного исправления ошибки (особенно если это был 2-й подход) — активируй **auto-verify**: проверка результата и, при необходимости, независимая верификация через bgagent (см. секцию «Независимая верификация через bgagent» там).
