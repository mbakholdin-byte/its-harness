# Verifier Pass — независимый критик (MiniMax Code)

## Назначение

Проверить результат **не тем же кодом, который его делал**. Оркестратор сам себя верифицировать
не может: свежий критик с изолированным контекстом — единственный способ поймать пропуск,
противоречие или выдуманный факт.

Канон: `VERIFIER_PASS` v1.6 §5 (механика) и §9 (точка подключения Mavis — этот плагин;
встроенный `agent.md` не годится: рантайм его перезаписывает).

## 1. Обязательный приёмочный шаг

Перед запуском критика — прогнать `scripts/verify_acceptance.py`:

```
python scripts/verify_acceptance.py --artifact ФАЙЛ [--task ФАЙЛ_ИЛИ_ТЕКСТ] \
    [--sources ФАЙЛ ...] --out БРИФ.md
```

Скрипт за одну команду:

1. **прогоняет канарейку гейтов** (`canary_gates.py --strict`) — гейты обязаны и пропускать
   хорошее, и отклонять плохое; неисправный гейт обесценивает любой вердикт;
2. **прогоняет `verify_gate.py`** на артефакте (placeholder'ы, секреты, пустота);
3. **проверяет формат вердикт-файла**, если он уже есть рядом;
4. **собирает бриф** в форме HANDOFF_PACKET: `goal` (исходная задача дословно), `sources`
   (требования/документы), `result` (артефакт или его содержимое), `constraints`, `return`.

Если шаг 1 или 2 не зелёные — критику отдавать нечего: сначала чинить артефакт или инструменты.

## 2. Три input'а для критика

По VERIFIER_PASS §5 критик получает ровно три вещи:

1. **Исходная задача** — дословно, как была поставлена (не пересказ оркестратора).
2. **Результат исполнителя** — полный текст/код/файл.
3. **Источники/требования, на которые опирался исполнитель** — документ, файл, норма, спецификация.

Третий input добавлен по предложению Mavis: критик без «что было до» слеп к выдуманным
цифрам и нормам.

## 3. Инструкция критику — verbatim

> «Проверь соответствие результата постановке. Найди: (1) пропуски против требований,
> (2) противоречия внутри результата, (3) непроверенные утверждения (цифры, цитаты, нормы —
> особенно без источника), (4) fabrication-risk. Верни вердикт строго в одном из форматов:
> `OK`, `LIST[замечания]`, `ESCALATE[причина]`. НЕ предлагай альтернативное решение.
> НЕ меняй scope задачи.»

## 4. Механика MiniMax Code

- Инструмент: `task` с ролью `verifier` — **свежий изолированный субагент**, не продолжение
  текущей сессии (`resume ≠ fresh`: критик не должен видеть внутренний контекст исполнителя).
- Роли `explore` и `verifier` — read-only; `worker` — единственная пишущая роль.
- Бриф уходит **в теле промпта** субагента (не файлом, не «разберись сам»).
- Продолжение той же задачи — `task_append`; чтение вывода — `task_output`.

## 5. Вердикт

Критик возвращает вердикт **файлом** по канону `skills/verdict-file/SKILL.md`:
первая строка `verdict: PASS|FAIL|ESCALATE`, секции «Проверял» / «Не сошлось» / «Не проверял».
Маппинг: `OK` → PASS, `LIST[замечания]` → FAIL, `ESCALATE[причина]` → ESCALATE.
Формат проверяется `scripts/verdict_gate.py` — PASS ставит только скрипт.

Зоны записи: **критик пишет только файл вердикта**; оркестратор правит артефакт по замечаниям
и **не пишет в файл вердикта ни строки**.

## 6. Чек-лист приёмки (обязательные пункты)

1. Приёмочный пакет собран (`verify_acceptance.py` → exit 0), канарейка зелёная.
2. `verify_gate.py` на артефакте → exit 0.
3. Критик — свежий изолированный субагент с ролью `verifier`, получил все три input'а.
4. Файл вердикта создан и прошёл `verdict_gate.py`.
5. Вердикт `PASS` — секция «Не сошлось» пуста; при `FAIL` — замечания с severity/area/claim/evidence.
6. Замечания minor — правит оркестратор; critical/major — максимум один цикл исправления,
   затем эскалация (стоп, не бесконечный цикл).
7. В ответе пользователю — путь к вердикт-файлу и сам вердикт, без самоотчёта вместо гейта.

## 7. Запреты

- Нельзя выдавать свой же результат за проверенный: проверяет другой контекст.
- Нельзя пропускать шаг 1 (канарейка) «ради экономии времени».
- Нельзя править артефакт и одновременно писать вердикт за него.
- Нельзя расширять scope критику и требовать от него альтернативное решение.
- Нельзя объявлять PASS без прогона `verdict_gate.py`.
