# Agent Dispatch — канон делегирования (MiniMax Code)

Канон общий (`_infra\shared\HANDOFF_PACKET.md` v1.0), механика вызова — здесь.

## 1. Когда делегировать

**Режим 1 — «делаю сам».** Задача укладывается в 1–4 вызова инструментов, не трогает
несколько файлов и не требует свежего взгляда. Делегирование не окупается.

**Режим 2 — «делегирую субагенту».** Задача многошаговая (>5 шагов), читает/пишет несколько
файлов, параллелится, или требует независимой проверки.

> Задача, где следующий исполнитель получает полный контекст предыдущего в той же цепочке, —
> это не делегирование, а внутренний шаг. Бриф не пишется.

## 2. Пакет передачи (бриф) — вход

Пять полей обязательны. Пустое обязательное поле («не знаю sources») — повод сначала найти
источник или вернуть вопрос оркестратору, а не стартовать вслепую.

| Поле | Содержание |
|---|---|
| `goal` | Что требуется сделать и зачем. Задача пользователя — дословно, без перефразировки |
| `sources` | Где актуальные исходники (точные пути) и их статус (оригинал/копия, версия) |
| `constraints` | Границы записи, доступы, бюджет, сроки, внешние действия |
| `result` | Ожидаемый артефакт или ответ + критерии готовности |
| `return` | Куда вернуть результат: путь, получатель, формат |

Опционально: `context` (минимальный предметный контекст), `decisions` (подтверждённые решения),
`owner` (кто принимает общий результат), `status` (стадия, незакрытые вопросы).

Бриф уходит **в теле промпта** субагента — не файлом и не «разберись сам».

## 3. Пакет возврата — выход

Возврат без доказательств — повод для дозаполнения, а не для показа пользователю.

- `СДЕЛАНО:` что реализовано (со ссылками на файлы/артефакты)
- `РЕЗУЛЬТАТ:` точный путь/ссылка на итоговый артефакт
- `ПРОВЕРКА:` по каким критериям проверено + команды и коды выхода
- `НЕ СДЕЛАНО:` что осталось и почему (если всё закрыто — явно «ничего»)
- `ПРОБЛЕМЫ:` что обнаружено по ходу, даже если обошёл
- `ПРОЦЕДУРЫ:` соблюдены ли регламенты (да/нет; где отступил — где именно)

## 4. Серийность

- **Запись** — последовательно: пишущие субагенты не идут в одну зону параллельно.
- **Чтение** — параллельно: независимые read-only ветки запускаются одновременно.

## 5. Верификация (verifier-pass)

После возврата исполнителя — **второй субагент со свежим контекстом** (роль `verifier`).
Resume ≠ fresh: критик не должен видеть внутренний контекст исполнителя.

На вход критику: (1) исходная задача дословно, (2) результат исполнителя,
(3) источники/требования, на которые опирался исполнитель.

Инструкция критику — verbatim:

> «Проверь соответствие результата постановке. Найди: (1) пропуски против требований,
> (2) противоречия внутри результата, (3) непроверенные утверждения (цифры, цитаты, нормы —
> особенно без источника), (4) fabrication-risk. Верни вердикт строго в одном из форматов:
> `OK`, `LIST[замечания]`, `ESCALATE[причина]`. НЕ предлагай альтернативное решение.
> НЕ меняй scope задачи.»

Вердикт оформляется файлом по канону `verdict-file` (первая строка `verdict: PASS|FAIL|ESCALATE`),
проверяется скриптом `scripts/verdict_gate.py`.

## 6. Механика MiniMax Code

- Инструмент: `task` с ролями `mavis` / `explore` / `worker` / `verifier`.
- Параллельные read-only ветки — несколько `task` в одном шаге (разные файлы).
- Продолжение дочерней задачи — `task_append`; чтение вывода — `task_output`;
  остановка — `task_stop`. Отменённая задача не должна возвращать «частичный PASS».
- `explore` и `verifier` — read-only роли. `worker` — единственная пишущая роль.

## 7. Запреты

- Нельзя делегировать задачу без acceptance-критериев — «сделай хорошо» не критерий.
- Нельзя передавать бриф прозой «разберись сам».
- Нельзя принимать возврат с самопохвалой без путей и доказательств проверки.
- Нельзя запускать двух пишущих субагентов в одну зону одновременно.
- Нельзя выдавать результат субагента за свой, не проверив его hard-гейтом
  (`scripts/verify_gate.py`).

## 8. Связанные каноны

- `КАТАЛОГ_КАНОНОВ\HANDOFF_PACKET.md` — контракты брифа и возврата (протокол выше механики)
- `КАТАЛОГ_КАНОНОВ\VERIFIER_PASS.md` — семантика проверки (что именно ловит критик)
- `skills/verdict-file/SKILL.md` — формат файла вердикта
- `docs/TRUTH_SOURCES.md` — где лежит канон, если формулировки расходятся
