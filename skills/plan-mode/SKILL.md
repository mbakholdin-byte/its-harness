# Plan-Mode: Режим планирования

**Обновлено:** 2026-10-03 — добавлен «Контракт валидации» как обязательная часть плана и гейт приёмки (по разбору доклада Factory Missions, AI Engineer Europe 2026).

## Назначение

Формализованный режим планирования для сложных задач. Агент сначала создаёт структурированный план с acceptance criteria, показывает пользователю, и только после подтверждения начинает выполнение.

**Отличие от стандартного подхода:** Без plan-mode агент может начать делать «как получится». Plan-mode обязывает зафиксировать критерии успеха до начала работы.

## Когда активировать

| Критерий | Активировать | Пропустить |
|----------|--------------|------------|
| Пользователь просит план | Да | — |
| Файлов затронуто | 5+ | <5 |
| Разработка кода | Да | — |
| Несколько этапов | Да | — |
| slash-команда /plan | Да | — |
| Пользователь: «быстро», «прямо сейчас» | Нет | Да |
| Простой запрос (поиск, чтение) | Нет | Да |
| Тривиальная правка (1-2 файла, <20 строк) | Нет | Да |

## Алгоритм (5 шагов)

### Шаг 1 — Сбор требований

1. Проверить, достаточно ли информации для планирования
2. Если недостаточно — задать 2-3 уточняющих вопроса (не больше!)
3. Определить scope: что ВХОДИТ и что НЕ входит в задачу

**Вопросы должны быть конкретные:**
- ✗ «Какой функционал вам нужен?» (слишком широко)
- ✓ «API должно быть REST или GraphQL?» (конкретно)

### Шаг 2 — Формирование плана

Структура плана:

```markdown
## План: {название}

### Цель
{Одно предложение — что получим в результате}

### Контракт валидации (acceptance criteria)
- AC1: {проверяемое утверждение} → доказательство: {команда/действие}
- AC2: {проверяемое утверждение} → доказательство: {команда/действие}
- AC3: {проверяемое утверждение} → доказательство: {команда/действие}

### Шаги
1. {шаг} → файл: {путь} → проверка: {как убедиться} → покрывает: AC1
2. {шаг} → файл: {путь} → проверка: {как убедиться} → покрывает: AC2
3. {шаг} → файл: {путь} → проверка: {как убедиться} → покрывает: AC3

### Risks
- {потенциальная проблема} → митигация: {решение}

### Out of scope
- {что НЕ делаем}
```

**Контракт валидации — главная часть плана** (принцип Factory Missions: «done» определяется до написания кода):

- AC фиксируются ДО начала работы и не переписываются под результат. Тест, написанный после реализации, подтверждает решение, а не ловит ошибку.
- AC — утверждения о поведении/результате, независимые от способа реализации («скрипт X с аргументом Y завершается кодом 0 и создаёт Z»), а не «код выглядит правильно».
- Покрытие двустороннее: каждый шаг ссылается на AC, которые он закрывает; каждый AC закрыт хотя бы одним шагом. AC без шага — план неполон; шаг без AC — кандидат в out of scope.
- Каждый AC проверяем извне: доказательство — конкретная команда, код выхода, наличие файла/строки, а не самоотчёт агента.

**Требования к плану:**
- Полные пути к файлам (не «создать скрипт», а «создать C:\MyAI\_infra\scripts\X.py`)
- Атомарные шаги (один файл, одно действие)
- Без TBD, «и так далее», «подобные изменения»
- Каждый AC должен быть проверяемым (доказательство = конкретная команда или действие)

### Шаг 3 — Презентация плана

Показать план пользователю:

> План готов.
> 
> **Цель:** [одно предложение]
> **Шагов:** N
> **Время:** [оценка]
> 
> Начинаем выполнение или нужно что-то изменить?

**Ждать ответа пользователя перед выполнением.**

### Шаг 4 — Выполнение

1. После подтверждения — создать todowrite из шагов плана
2. Выполнять по шагам, отмечая прогресс
3. При отклонении от плана — предупредить пользователя и спросить подтверждение
4. Если обнаружена проблема — вернуться к Шагу 3 (пересмотреть план)

### Шаг 5 — Приёмка (гейт)

После выполнения — проверить каждый AC контракта. Это гейт: «готово» объявляется только когда все AC — PASS.

```
План выполнен.

AC1: PASS (проверка: результат команды X, код выхода 0)
AC2: PASS (проверка: файл существует по пути Y)
AC3: FAIL (причина: не удалось Z)

FAIL: [описание проблемы]
Рекомендация: [что сделать]
```

**Правила гейта:**
- AC, который нельзя подтвердить внешним доказательством, считается FAIL, а не «вроде работает».
- Недоработка НЕ заметается молчаливой правкой: либо дорабатываем по месту с явной пометкой в отчёте, либо оформляем новой задачей/шагом плана — с записью, что контракт изначально не закрыт.
- Если по ходу работы выяснилось, что AC сформулирован неверно — контракт пересматривается через Шаг 3 (с подтверждением пользователя), а не задним числом.

## Пример из работы

**Запрос:** «Сделай систему мониторинга тендеров»

**План:**

```
## План: Система мониторинга тендеров

### Цель
Автоматический мониторинг тендеров НПО ИТС на zakupki.gov.ru с сохранением в SQLite

### Acceptance Criteria
- AC1: Скрипт запускается без ошибок → проверка: `python tender_monitor.py --test`
- AC2: Данные сохраняются в SQLite → проверка: `sqlite3 tenders.db .tables`
- AC3: Результат соответствует запросу «НПО ИТС» → проверка: визуальная проверка 5 записей

### Шаги
1. Создать структуру проекта → файл: C:\MyAI\_infra\tender_monitor\main.py → проверка: импорт без ошибок
2. Реализовать API-клиент zakupki → файл: C:\MyAI\_infra\tender_monitor\api_client.py → проверка: curl-запрос работает
3. Добавить SQLite-хранилище → файл: C:\MyAI\_infra\tender_monitor\storage.py → проверка: таблица создана
4. Сделать CLI-интерфейс → файл: C:\MyAI\_infra\tender_monitor\cli.py → проверка: --help работает

### Risks
- zakupki.gov.ru блокирует частые запросы → митигация: задержка 1 сек между запросами
- Large Excel файлы → митигация: обработка в streaming-режиме

### Out of scope
- Веб-интерфейс (только CLI)
- Уведомления (только сохранение в БД)
```

## Антипаттерны

- **НЕ** начинать выполнение до подтверждения плана
- **НЕ** делать план тривиальной задачи (трата времени)
- **НЕ** включать в план «и так далее» — каждый шаг должен быть конкретным
- **НЕ** пропускать AC — без критериев непонятно, когда задача завершена
- **НЕ** изменять план без предупреждения пользователя

## Связь с AGENTS.md

Расширяет правило AGENTS.md: «Планировать ОДИН РАЗ в начале, отчитываться о прогрессе относительно плана».

- **AGENTS.md** — общий принцип планирования
- **plan-mode** — формализованная процедура с шаблоном и подтверждением
